# 007 · AI 参与测试与修复的风险分级

- 状态：Accepted
- 日期：2026-08-28
- 关联模块：横切 · Testing & Quality / 与 [ADR-006](006-sandbox-vs-oj.md) 的沙盒决策共同守护安全边界

## 背景

社区流行的 "Vibe Coding" 主张把测试也纳入人机对话闭环——AI 写代码、AI 写测试、AI 跑测试、AI 读报错、AI 自主修复,直到全部通过,人只在验收环节介入。DeepEval / Vibetest / yo-bug / Katalon Scout 等工具都在推动这个模式。

FEDrill 是否也全盘拥抱这套?给出一个决策,以免之后每次改动都要临时判断"这次让 AI 修不修"。

关键约束:

- FEDrill 有 **两块高风险表面**——Web Worker 沙盒(跑用户代码,逃逸=用户 XSS)和 LLM 引导 prompt(改一个字 eval 分全变,AI 走捷径概率高)
- FEDrill 有 **一块隐形风险**——LLM 成本 / 延迟相关代码,AI 为通过测试可能悄悄加缓存降级,改动产品语义
- FEDrill 又有 **大片低风险区域**——工具函数、UI 组件、类型定义,完全适合让 AI 全闭环

## 候选方案

| 方案 | 谁写测试 | 谁跑测试 | 谁修 bug | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| **A · 全盘 Vibe 闭环** | AI | AI 自主 | AI 自主循环 | 效率最高;人只做验收 | 沙盒/prompt/成本三处 AI 可能"让测试过"但产品坏掉 |
| **B · 传统人肉** | 人写(AI 辅助) | 人跑 | 人修(AI 建议) | 每步可控 | 慢;低风险区效率浪费;和简历叙事(AI 工程化)不符 |
| **C · 按风险分层** | 因区而异 | 因区而异 | 因区而异 | 高风险守得住,低风险跑得快 | 决策成本:每次改动要判断在哪个 tier |

## 决定

**采用方案 C · 按风险分层**,并把 tier 划分写死到本 ADR,消除"每次临时判断"的成本。

### 三档分级

#### Tier 1 · 低风险 · AI 全自动闭环

**范围**:
- `lib/utils/`、`lib/types/`、通用 hooks
- UI 组件(纯展示、无副作用)
- 样式、动画、a11y 属性
- 文档、注释、README

**AI 行为**:写代码 + 生测试 + 跑 `pnpm test:watch` + 读失败 + 自主修 + 再跑,循环直到绿。人只 review 最终 PR diff。

**约束**:
- 修复循环最多 5 轮,超出必须停下来问人
- 每轮 diff 累计超过 100 行必须停下来问人

#### Tier 2 · 中风险 · AI 写代码 + AI 跑测试 + 人审修复

**范围**:
- `app/api/**/*` Route Handler
- `lib/agent/` Agent Loop 逻辑(状态机、tool 调度、SSE 编排)
- `lib/harness/` LLM 调用与流处理
- `lib/repo/` 数据层(SessionRepo 等)
- 交互性 UI(Monaco 集成、chat 输入、run/submit 按钮)

**AI 行为**:AI 写实现 + AI 生测试 + AI 跑。**测试失败时 AI 不自动修**——它只输出「诊断 + 修复方案 + diff 预览」,由人拍板哪个方案,由人合入。

**理由**:这块出错不至于人身安全或财务风险,但 AI 自主修容易改坏交互细节;人多花 30 秒看 diff,产品语义可控。

#### Tier 3 · 高风险 · AI 只诊断 · 人亲手改

**范围**:
- `lib/sandbox/` Web Worker 沙盒、`new Function` 执行链、超时/kill、消息协议
- Round 0-4 追问 prompt 本体(`lib/agent/round*-prompt.ts`)
- LLM 成本/超时/降级/缓存策略
- 认证、鉴权、密钥读取(M4 起有用户系统)
- 环境变量、`.env` 处理、密钥泄漏防护

**AI 行为**:AI 可以指出「测试挂在哪里、可能原因是什么、有几种修法及各自权衡」,**不允许自动提交 diff 到这些路径**。人手写修复,人补测试用例(可以让 AI 生用例草稿再筛)。

**理由**:
- 沙盒 bug 的失效模式是「测试过但真攻击成功」——AI 为让 red-team 用例过,可能加一层拦截,但没堵住变种。安全代码要人来看每一行含义。
- Prompt 改动 AI 有强动机走捷径:测试要求「Round 0 不能给完整答案」,AI 可能在 system prompt 里塞一大段禁止条款,eval 分过了,但真实对话里 LLM 也变得死板不引导。人来改能感知这种副作用。
- 成本/降级代码 AI 不知道你钱包深度和用户体验优先级排序,让它自己判断=让它替你做业务决策。

### 强制护栏(所有 tier 通用)

1. **不允许 AI 修改 `docs/decisions/`**——ADR 是历史事实,只能追加新的 supersede 而不是改老的
2. **AI 生成的测试要人过一遍语义**——防止「测了实现而非行为」的假测试
3. **测试挂了不能 AI 自己 `.skip()` 或注释掉**——只能报告,由人决定是修 bug 还是修测试
4. **Prompt 相关的 eval 分回归超过 10% 强制人介入**——不允许 AI 优化 prompt 让分数回来

## 落地映射(和 6 步测试栈的对应)

| 6 步落地阶段 | Tier 1 覆盖 | Tier 2 覆盖 | Tier 3 覆盖 |
|---|---|---|---|
| Step 1-2 · Vitest 单测 | utils / 纯函数 | SSE 解析、Agent Loop | sandbox `deep-equal` 已存在 |
| Step 3 · Playwright E2E | 样式冒烟 | 手撕题闭环、chat SSE | 沙盒红队 E2E |
| Step 4 · Playwright MCP | AI 自主跑冒烟 | AI 辅助跑业务流程 | 禁用于沙盒验证 |
| Step 5 · 沙盒红队 | — | — | **全部 Tier 3**,只人写 |
| Step 6 · promptfoo eval | — | tool 调度准确率 | **prompt 本体属 Tier 3**,人手调 |

## 理由(四条,按权重排列)

### 1. 沙盒安全是不可逆风险

沙盒逃逸 → 用户 XSS → 一次事故品牌信任崩塌 + 秋招简历上「上线过 AI 教练」变成负资产。AI 自主修沙盒 bug 有强动机通过测试但不堵变种,这类风险的期望损失远大于人肉修的时间成本。

### 2. Prompt 是 FEDrill 的产品核心

Round 0 追问是 FEDrill 相对通用 AI 工具的**唯一差异化**([项目调研.md](../项目调研.md) 明确「三种 AI 教练形态」是核心壁垒)。Prompt 由 AI 自主优化 = 把核心产品心智交给 AI,失去人的品味把关。这条比技术风险更致命。

### 3. 低风险区不 Vibe 化 = 白扔效率

绝大多数 utils / hooks / 类型代码没有产品语义,人肉写测试 = 浪费。让 AI 全闭环这些区域,面试时可以直接讲「我在 FEDrill 里用了 Claude Code 自主闭环写 XX 层,速度提升了 Y」——本身就是简历亮点。

### 4. 分级消除决策疲劳

如果每次改动都问「这次让 AI 修不修」,大脑很快就疲了,最后要么全拒绝要么全接受。**把 tier 提前写死**,以后只需查表:改到哪个路径 → 走哪档流程。

## 后果

**正面**:
- 高风险区安全可控
- 低风险区速度最大化
- 每次修改的流程明确,减少心智负担
- **简历叙事强化**——「我按风险分级引入 AI 自主闭环」是比「我全盘 Vibe Coding」更成熟的说法

**负面**:
- 需要每季度回顾一次 tier 划分是否需要调整(比如某个 lib 从原型期到稳定期,可能从 Tier 2 降到 Tier 1)
- 有些代码在灰色地带需要判断(比如 `lib/repo/` 涉及 localStorage,可能未来涉及敏感数据),暂时判 Tier 2,视演化调整
- 团队协作时(未来招人 / 开源)需要新人先读这份 ADR
